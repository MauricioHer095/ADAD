EXPLICACIÓN DE LA BITÁCORA: LÍNEA BASE (LABORATORIO 1.1)
Archivo analizado: availability-baseline.txt
Configuración: CatalogResource sin patrones de resiliencia (sin @Timeout, @Retry, @Fallback ni @CircuitBreaker).

1. Qué se midió
Esta bitácora se generó en el laboratorio 1.1 con el script test-availability.ps1, que manda 200 peticiones GET a http://localhost:8081/v1/products y guarda por cada una el número de petición, el código HTTP, el tiempo total (time_total de curl, en segundos) y el cuerpo de la respuesta. Sirve como punto de comparación para todas las etapas del laboratorio 1.2.

2. Resultados
- Respuestas SUCCESS (HTTP 200): 145 de 200 (72.5 %).
- Respuestas HTTP 500: 55 de 200 (27.5 %).
- Disponibilidad observada: 0.725.
- Latencia promedio: 0.563 s. Mediana: 0.007 s. Percentil 95: 3.008 s. Máxima: 3.030 s.
- 37 peticiones tardaron alrededor de 3 segundos.

3. Interpretación
El servicio original simula tres casos: latencia alta de 3000 ms, falla de conexión a la base de datos y respuesta correcta. Como no hay ningún mecanismo de protección, cada caso llega tal cual al cliente.

Las fallas de conexión se convierten directamente en HTTP 500. Llama la atención que estos errores son rápidos (11 ms en promedio): el servicio falla de inmediato y el cliente se queda sin datos.

La latencia alta es el otro problema. Las 37 peticiones que tardaron unos 3 segundos sí terminaron en SUCCESS, pero el cliente tuvo que esperar todo ese tiempo, porque nada corta la operación. Por eso la mediana es muy baja (7 ms) y el percentil 95 sube a 3 segundos: la mayoría de las peticiones son rápidas, pero hay un grupo importante que se queda bloqueado.

En resumen, la línea base muestra los dos problemas que el laboratorio 1.2 busca resolver: casi una de cada cuatro peticiones termina en error y una parte considerable sufre esperas largas.
